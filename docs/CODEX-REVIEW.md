## 一句话问题

我在卡片里做的「阶段进度」是**写清单时手工标注的静态前缀**，而真实开发过程是动态的——任务会被新建、合并、废弃、重排。请帮我想清楚：**阶段信息应该从哪里来，才能既反映真实进展，又不需要人工维护？**

## 背景：这个插件做什么

每轮 AI 回复结束后，在回复下方渲染一张卡片，内容全部从会话日志（`~/.dsh/sessions/*.sessions` 的 zstd 事件流）推导，**不调用模型、不消耗 token**。

卡片包含：

| 区块 | 数据源 |
|---|---|
| 指标表格 | `tool/call`、`tool/result.isError`、工具参数里的文件路径 |
| 执行摘要 | `assistant/message.usage` + `message.source`（模型路由） |
| 本轮完成 | 对比本轮与上轮的 `todo_write` 快照差异 |
| 计划 HUD | 本轮 `todo_write` 快照，按组展示 |

技术栈：宿主侧 `sessionProjections`（事件溯源折叠）+ 浏览器侧 `conversation.chat.turnTail` 槽位渲染。

## 现在怎么做的（以及为什么不够）

### 数据源的硬限制

`todo_write` 工具（模型用来写任务清单）的事件载荷长这样，**没有层级、没有阶段、没有 id**：

```json
{
  "todos": [
    { "content": "【阶段一·实现】index.js 新增 stageOf", "status": "completed" },
    { "content": "【阶段二·清理】阶段前缀剥掉", "status": "completed" },
    { "content": "【阶段四·待办】重启确认", "status": "pending" }
  ]
}
```

只有 `content`（字符串）和 `status`（`pending` / `in_progress` / `completed`）两个字段。整表覆盖写（last-write-wins），无稳定 id。

### 我目前的实现

因为数据里没有阶段，我让**写清单的人（AI）在 content 里打标记**：

```
【阶段一·实现】xxx
〔P1〕yyy
[阶段2] zzz
```

插件用正则解析前缀，把第一段括号内容当阶段名分组（`index.js:463 stageOf()`），组内状态由该组任务状态聚合：全完成 → ✅、有进行中 → ⏳、都没开始 → ⬜。

### 为什么用户说"框死了"

1. **阶段是写的时候定死的**。开发中途发现要拆成两个阶段、或原定的阶段二根本不需要做，前缀不会自己变——除非 AI 每轮手动重写整张清单。
2. **实测 AI 只有 26% 的轮次会调 `todo_write`**（另一个会话 6%）。其余轮次卡片只能复用上轮快照，并标注"本轮未更新"。所以阶段信息天然是陈旧的。
3. **重命名会丢历史**。`todo_write` 无 id，跨轮匹配只能按文本比对（`index.js:264 matchKey()`，剥掉符号/空白/大小写）。改了措辞就等于新任务。
4. **阶段粒度靠人拍**。写清单时没有依据决定"这算一个阶段还是三个"。

## 请帮判断的关键问题

### Q1. 阶段到底该从哪来？

我想到几条路，但都不确定：

| 方案 | 做法 | 顾虑 |
|---|---|---|
| A. 保持前缀标注 | 现状，AI 写清单时标 | 需要人工维护，容易过时 |
| B. 从行为推导 | 用工具调用、文件修改、时间间隔聚类出阶段 | 聚类结果未必符合人类认知的"阶段" |
| C. 用对话自身结构 | 用户消息 / 模型的 thinking 里通常有"接下来做X"的叙述 | 需要解析自然语言，但**不消耗额外 token**（已有数据） |
| D. 放弃"阶段"，改做时间线 | 不分组，按轮次展示进展轨迹 | 可能更诚实，但用户要的是"阶段进度" |
| E. 混合 | 有前缀用前缀，没有就从行为推导兜底 | 复杂度高，两种语义可能冲突 |

**我的倾向**：C 可能被低估了。模型的 `reasoning` 内容和用户消息里其实有大量"我现在在阶段二"的自然语言信号，而这些数据已经在会话日志里，解析它们不需要额外成本。但我不确定解析的可靠性。

### Q2. 阶段应该是"演进的对象"还是"视图"？

两种完全不同的定位：

- **演进的对象**：阶段像里程碑，会被创建、完成、废弃。需要一个持久化的阶段表。
- **视图**：阶段只是"当前任务按某种规则分组后的呈现"，每轮重新计算，不持久化。

现在的实现是后者（每轮从快照重算），但用户期待前者（阶段是项目的一部分，应该记住）。**如果选前者，就需要在投影里维护一张阶段表，而 `todo_write` 无 id 会让这张表很难稳定。**

### Q3. 动态改动怎么处理？

真实场景里会发生的：

- 阶段二被拆成两半
- 阶段三四五合并
- 某阶段做到一半发现方向错了，整个废弃
- 原本以为是阶段的任务，做着做着变成独立项目

现在这些改动**全都表现为"下一轮的清单不一样了"**，插件无法区分"改进了"和"改错了"。

## 已验证的环境事实（避免重复踩坑）

| 项 | 事实 |
|---|---|
| 安装方式 | profile 里必须是 **junction**。pnpm 会装成拷贝，导致改源码不生效且毫无报错 |
| 自检脚本 | `tools/check-install.ps1`（需 UTF-8 BOM，PS 5.1 才认中文） |
| bundle id | 必须等于 profile 依赖名 `@nethiel/dsh-turn-report`，与 `package.json.name` 一致 |
| 事件解码 | 会话日志是**多帧 zstd**，按 magic `0xfd2fb528` 逐段解 |
| 状态校验 | 改完必须查 `session_projcache` 里的 `ver` 与 `groups` 实况，不能只看单测 |
